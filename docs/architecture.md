# 架构、协议与开发参考

本文档记录 `v2echo-notifier-cf` 的系统契约、安全与隔离边界、API 行为以及本地测试与源码入口。部署与运维步骤请见 [部署、升级与运维指南](deployment.md)。

---

## 管理台结构与会话

管理台基于 React 19、Vite、Tailwind CSS v4 与 shadcn/ui（沿用 `shadcn-admin` 视觉基线）：

- **动态**：**概览**（服务状态、指标卡、近 7 天运行趋势、最近通知与三类监测通道状态）、**个人消息**（缓存消息与已读历史翻页）、**关注帖子**（主题评论提醒规则）、**关注成员**（成员新帖提醒开关与动态列表）。
- **记录**：**推送记录**（投递状态、密文按需展开与回执明细）、**检查日志**（按来源与结果筛选执行日志，支持异常提示与一键清除红点）。
- **系统**：**设置**，内部按 5 个分区组织：
  - **通知策略**：服务启停、每日检查时段与三类间隔、发送测试通知；
  - **账号与凭据**：多账号增删与切换、Cookie / PAT 更新与手动验证；
  - **设备配对**：生成配对二维码、添加接收设备、接替旧助手、撤销单台设备的关注管理授权；
  - **网络与诊断**：HTTP / SOCKS5 代理配置与连通测试、手动执行到期检查、Worker / D1 / V2EX API 用量、当前版本展示与手动检查更新；
  - **外观**：亮暗模式、主题色与侧栏布局。

管理员登录使用 `ADMIN_TOKEN` 换取 30 天有效期的 `HttpOnly` 会话 Cookie；退出登录清除当前会话，修改 `ADMIN_TOKEN` 会使全部旧会话立即失效。写操作要求同源 `Origin` 与 `X-Notifier-Request: 1` 请求头；程序化调用也可使用 `Authorization: Bearer <ADMIN_TOKEN>`。

### 版本与手动更新检查

- 构建时通过 `vite.config.ts` 将 `APP_VERSION`（默认取 `package.json` 的 `version`，发版流水线按 Git Tag 覆盖）静态注入前端与 Worker；已鉴权的 `GET /api/accounts/:id/state` 返回 `version` 字段，匿名的 `/api/app/v1/health` 不暴露版本号。
- `GET /api/version/check`（仅管理员鉴权可访问）仅在用户手动点击「检查更新」时请求 `https://api.github.com/repos/wizcheu/v2echo-notifier-cf/releases/latest`（禁止跟随重定向、8 秒超时、64 KiB 响应上限、不携带任何用户凭据、不在后台 Cron 自动调用），保持浏览器 `Content-Security-Policy: connect-src 'self'` 严格策略不变。

## 多账号与隔离

单个实例最多管理 **20 个**已验证 V2EX 账号。所有账号共用管理登录、网络代理、加密主密钥 `NOTIFIER_KEY` 与助手实例身份；Cookie / PAT、扫描状态、检查策略、未读快照、历史缓存、去重记录、关注规则、发送凭据与设备管理授权均按账号严格隔离。

- 数字会员号是账号身份；本地 `id` 不可变且不复用；用户名仅用于展示与辅助核验。
- 在 **设置 → 账号与凭据** 填写各账号自己的 Cookie 与 PAT，验证身份一致且不重复后原子入库。侧栏左上角与左下角均可切换当前账号；切号时立即作废在途页面请求、表单、二维码与分页状态，避免跨账号串显。浏览器仅持久化外观偏好，不保存凭据、邀请码或账号数据。
- 账号头像取自身份校验通过的首页当前账号卡，随既有首页检查更新并持久缓存；未取得有效头像时保留缓存。读取账号列表不访问 V2EX 上游。
- 同一手机可在 V2Echo App 登录账号 A 扫描 A 的配对码，再切换账号 B 扫描 B 的配对码。每个来源使用 `pairing_policy: explicit`，已有其他账号的复用连接不能代替新账号的逐账号配对；重新配对 A 不撤销 B。

| 管理接口 | 契约 |
| --- | --- |
| `GET /api/accounts` | 返回账号摘要与凭据配置状态，不返回凭据明文或密文。 |
| `POST /api/accounts` | 必须同时提交 `{cookie, pat}`；PAT 与 Cookie 身份一致且会员号未重复时原子保存并返回本地 `id`。 |
| `GET /api/accounts/:id/state` | 返回该账号的状态、异常计数、API 用量，以及实例共用的代理与资源统计。 |
| `/api/accounts/:id/notifier/*` | 该账号的验证、凭据、配对、扫描、历史、关注、记录查询与清除异常红点操作。 |
| `DELETE /api/accounts/:id` | 先暂停该账号，撤销当前与未完成配对的所有持久化 sender，再原子删除其本地业务数据。远端撤销失败时保留凭据与暂停状态以支持重试，不影响其他账号。 |

- 旧路径 `/api/state` 与 `/api/notifier/*` 仅指向迁入的本地账号 `id=1`，不跟随网页选号，也不会在 `id=1` 删除后回退到其他账号。App 直连路径 `/api/app/v1/*` 保持不变。
- 删除与在途配对依靠中央 sender 撤销墓碑保持隔离：撤销先于兑换、响应丢失或重复请求都不能恢复已删除的发送能力。已交给 APNs 的通知不可撤回，App 点击时仍校验本地保存的账号与绑定。

## 真实通知闭环

1. **凭据与身份核验**：准备同一账号的完整 Cookie 与 PAT，通过 **设置 → 账号与凭据** 验证并加密保存（旧 `id=1` 仍兼容历史 Worker Secrets 回退）。
2. **扫码配对**：通过公开 HTTPS 地址打开面板，在 **设置 → 设备配对** 生成 10 分钟有效的二维码。V2Echo App 扫码或粘贴后，确认助手 HTTPS 地址并直接完成个人提醒绑定与关注管理授权；请求前加密保存邀请码与短期设备证明，超时可在 App 重试。App 经中央核对绑定后才显示已连接。
3. **不标已读扫描**：以首页未读数限定 V2EX API v2 通知候选范围，逐页持久化扫描进度，多页完成后复查第一页。失败保留进度，首屏或未读数变化则重扫；全程不访问会标记已读的网页 `/notifications`。首次启动仅补发当前未读范围，不回放全部历史。
4. **去重与入队**：按 `SHA256(v2ex:<会员号>:<通知 ID>)` 精确去重并原子写入队列。每条通知独立推送，准备密文后固定标题与正文载荷。仅最新完整扫描中的未尝试事件可首次发送；已尝试事件保留原载荷继续重试。由于网页与 API 不存在原子未读快照，不承诺严格逐条已读判定。
5. **端到端加密上报**：默认向固定公开 HTTPS 入口 `https://app.v2echo.com/api/push` 提交事件，用户无需拥有中央 Worker 或同账号权限。每台设备独立使用 X25519 / HKDF-SHA256 / AES-256-GCM 加密标题与正文；首次设备公钥信任配对服务，已知公钥变化则停止准备新密文；目录读取失败不回退明文，合法空目录仅发送通用提示。
6. **幂等重试与回执**：未确认收件时重试完全相同的事件 ID 与密文；确认 `pending` 后仅按事件 ID 查询回执。重复、遗漏或非法状态的回执不推进事件；`not_found` 不触发重发；`apns_accepted` 仅代表 APNs 接收，当前 S2S 回执不返回设备显示或已读 ACK。一个推送连接内的设备须使用同一 APNs 环境。

### 服务开关、分类与测试通知

- **通知服务开关**：保存在 D1，刷新或重部署保留。暂停后停止自动检查、推送重试与回执查询（保留账号、配对、个人通知扫描进度 / 队列与退避；未提交的关注事件取消，恢复后重建关注基线不补历史）；Cron 仍执行数据库维护与低频连接同步。
- **通知分类**：按 API 动作句识别回复、提及、主题感谢、回复感谢与收藏（兼容中英文与 V2EX 子域链接）。未识别、冲突或感谢目标不明时标为「待分类」，保留加密预览但暂不推送，不阻塞其他通知也不写入永久去重。
- **测试通知**：在 **设置 → 通知策略** 支持个人五类测试及三类关注测试（「关注帖子 · 单条评论」「关注帖子 · 多条评论」「关注成员 · 新帖」）。个人测试优先复用当前账号缓存的真实样本（保留 7 天），无缓存时最多读取最近 100 条 API 通知取样，确认无匹配才使用合成示例；取样入队后立刻启用新租约尝试投递，遵守一分钟限频与 S2S 退避，不污染正式去重或未读状态。
- **发送者头像补齐**：若通知 API 仅返回用户名而缺头像，首次准备投递时可通过公开成员资料接口匿名补齐（不携带 Cookie / PAT，单次超时 3 秒，每轮最多补齐一个事件），白名单校验通过后随密文固定；失败保留文字不伪造头像。
- **限流与容量边界**：
  - S2S 每轮最多 20 条事件、50 条回执、64 KiB，至少间隔 30 秒加抖动；指数退避上限 1 小时并尊重最多 48 小时 `Retry-After`。真实事件有效期 24 小时，测试事件 15 分钟。
  - V2EX 网页（Cookie）与 API v2（PAT）独立诊断：明确 Token 失效提示更新 PAT；Cloudflare 1010 或人机验证至少退避 15 分钟；未明原因普通 403 按通道连续失败次数执行 1 / 2 / 5 / 15 分钟退避，不误判凭据失效。
  - 单轮候选上限 1,000 条、活动队列上限 2,000 条、精确去重上限 100,000 条、设备公钥固定上限 100 个。终态推送详情保留 7 天（约 10,000 条上限），精确去重独立保留，不通过删除去重制造重复推送。

## 关注提醒（iPhone / iPad）

需新版 V2Echo App、中央推送服务与本助手协同，沿用 Pro 个人远程提醒：

- **规则权威存储**：全部关注规则、单调修订号与幂等操作回执保存在用户自己的 D1（以 `NOTIFIER_KEY` 加密进度与缓存）；中央服务仅保存来源 / 接收关系、路由元数据与待取消事件 ID，不保留日常关注清单。
- **帖子评论提醒**：同账号绑定组最多关注 **20 篇**主题（含暂停项，全部接收设备共享，与 V2EX 原站收藏独立）。首次启用、重开或出现超过 24 小时检查缺口时建立尾部回复基线，不补已有评论；后续按稳定回复 ID 与真实楼层聚合非本人新评论，超过 200 条仍准确计数。
- **关注成员新帖**：在「关注成员」开启总开关后，从 `/?tab=members` 当前页发现候选帖子，并结合 `/my/following?p=1` 核对完整成员名单，再从主题详情校验真实作者与创建时间（顶帖、本人主题及新关注成员的旧帖不提醒）。该页面无历史分页，已滑出窗口的未采集帖子不保证补齐。
- **分片与调度预算**：每次关注分片最多检查 1 个最早到期目标、最多 3 次网页请求，25 秒后不再发起新请求，单响应上限 1 MiB；优先保障个人消息与回执。单条加密检查进度明文上限 512 KiB。
- **推送事件**：使用独立 `watch_update` 类型，不携带原站通知编号或未读数，不改角标；按设备公钥端到端加密，标题 / 正文分别截取前 100 / 180 个 Unicode 字符。

### App 直连接口与撤销

- `GET /api/app/v1/health`：匿名轻量存活检查，返回 `200 {"status":"ok"}`，不读取 Secrets、D1 或外部服务。
- `POST /api/app/v1/pair`：统一配对入口，查 D1 前限流 20 次 / 分钟 / IP。二维码格式为 `v2echo://notifier-pair?url=<HTTPS源地址>&code=<V2N邀请码>`（有效 10 分钟）。App 提交一次性设备证明与本机生成的 `client_id` / `client_secret`（不传中央设备 Secret、APNs Token 或 V2EX 凭据），助手校验并原子保存管理凭据哈希及完成回执（支持同组新来源的可选 `import_config` 迁移，不覆盖既有规则）。单账号最多 20 个管理连接，同设备重连自动替换旧管理凭据。
- `GET /api/app/v1/watches` / `PUT /api/app/v1/watches`：使用独立 Bearer 管理凭据，与后台采集共用租约与事务隔离，不授予网页管理员或通知发送权限。可在网页 **设置 → 设备配对** 撤销单台设备的管理授权。
- 删除或暂停规则后立即停止后续产生事件；已提交中央尚未交给 APNs 的事件经取消队列重试撤销（保留 2 天）；已交给 APNs 的通知不可撤回。

### 添加设备与更换助手

- **添加接收设备**：在已配对账号的 **设置 → 设备配对** 生成「添加接收设备」二维码，最多支持 10 台接收设备；仅追加当前设备，不重建来源或清空队列。
- **更换助手实例**：在**全新的未绑定助手**中生成 `V2T-` 更换二维码，用已绑定原助手的 iPhone / iPad 扫码授权切换来源、保留原组设备并撤销旧 sender；完成后再扫新助手的普通配对二维码取得管理授权。保留原 D1 与 `NOTIFIER_KEY` 的常规更新无需更换实例。

## 网页记录与历史接口

- **推送记录**（`GET /api/accounts/:id/notifier/records?view=deliveries`）：支持状态与来源筛选，每页 20 条游标分页；点击条目经 `GET /api/accounts/:id/notifier/events/:eventId` 按需解密标题与正文。
- **检查日志**（`GET /api/accounts/:id/notifier/records?view=checks`）：记录 `scan`、`following_topic`、`topic_reply` 等执行结果，支持按来源与结果（含 `outcome=issues` 筛选 `error` / `interrupted`）游标分页。保留 7 天、上限约 5,000 条；异常中断在小时维护时将超时 120 秒未完成的记录标为 `interrupted`。
- **异常计数与清除红点**：
  - `GET /api/accounts/:id/state` 中的 `notifier.check_errors` 统计状态快照前 24 小时内、且 `started_at > check_errors_acked_at` 的三类业务检查（`scan` / `following_topic` / `topic_reply`）的 `error` 与 `interrupted` 次数。
  - `POST /api/accounts/:id/notifier/checks/ack` 用于一键清除红点：不占用全局扫描租约，将 `check_errors_acked_at` 推进至当前近 24 小时内最新已完成异常的 `started_at`（不删除任何历史日志，也不吞掉在途尚未结束、稍后失败的检查）。
- **个人消息缓存与历史拉取**：
  - 进入页面与翻页经 `GET /api/accounts/:id/notifier/messages` 仅读 D1 缓存（保留 7 天、约 1,000 条上限），不请求 V2EX。
  - 「获取最新数据」/「获取更早消息」调用 `POST /api/accounts/:id/notifier/history`（`{page}` 限 1–9,999），只读 `/api/v2/notifications?p=` 并按需匿名补齐作者头像（单次最多查询 10 位作者、25 秒预算），不触碰网页已读状态、不入推送队列。
- **独立未读快照接口**：`GET /api/accounts/:id/notifier/unread` 读取最近一次完整未读快照；`POST /api/accounts/:id/notifier/unread/refresh` 分页刷新完整快照（上限 1,000 条，新一轮间隔 60 秒），独立于推送扫描队列。
- **关注主动刷新**：`POST /api/accounts/:id/notifier/watch/refresh` 逐轮主动检查关注目标，跳过日常检查间隔与时段，仍遵守失败退避与上游限制（连续最多 100 轮）。

## 访问凭据

- **设置 → 账号与凭据** 默认仅展示凭据配置状态（来源与更新时间），不回显明文或密文。
- `PUT /api/accounts/:id/notifier/credentials` 接收 `{cookie?, pat?}`，留空项沿用原值；Cookie 上限 16 KiB，PAT 上限 4 KiB，请求体上限 64 KiB。
- 更新前须先通过 PAT 的 `/api/v2/member` 与 Cookie 首页用户名核验，确认与当前记录的数字会员号一致后才在租约事务内以 `NOTIFIER_KEY` 加密写入 `notifier_credentials`；验证失败保留旧凭据与旧进度。
- 网页加密保存的凭据优先级高于部署 Secrets；历史部署 Secrets（`V2EX_COOKIE` / `V2EX_PAT`）仅作为原 `id=1` 无网页记录时的兼容回退。

## 网络代理

在 **设置 → 网络与诊断** 可配置 `http://主机:端口`（需支持 CONNECT）或 `socks5://主机:端口`（由代理解析域名，支持无认证或账密认证），默认关闭：

- 启用后，V2EX 网页、官方 API、配对、推送健康检查、事件发送与回执查询统一经代理出口；D1 与浏览器到管理台的请求不走代理。
- 配置使用 `NOTIFIER_KEY` 加密保存于 D1；`GET /api/proxy-settings` 仅返回地址与启停状态，`PUT /api/proxy-settings` 保存、切换或清除，`POST /api/proxy-settings/test` 在不保存、不带 Cookie / PAT 的前提下测试连通 `https://www.v2ex.com/`（12 秒超时、1 MiB 上限）。
- 目标站点仍端到端走 HTTPS，由固定版本 `tunnelfetch` 在隧道内校验证书、主机名与有效期；配置解密、连接或证书错误均中止请求，不静默回退直连。代理模式含用户态 TLS 开销，需在目标 Workers 套餐下实测 CPU 耗时。

## 通知调度与资源边界

- **检查时段与间隔**：按固定北京时间（UTC+8）整点配置，默认 **08:00–24:00**（支持跨午夜，`00:00–24:00` 表示全天）。默认间隔：未读消息 `3` 分钟（可选 3 / 5 / 10 / 15）、关注成员 `10` 分钟（可选 5 / 10 / 15 / 30）、关注帖子 `5` 分钟（可选 5 / 10 / 15 / 30 / 60）。帖子连续无新增达 6 / 12 次时自动降频至 30 / 60 分钟，有新增后恢复用户设置。
- **时段外行为**：不启动首页扫描、通知分页或自动核验，仅继续处理符合条件的已入队推送、重试、回执与数据库维护；管理员手动验证、读取历史与发送测试不受检查时段限制。
- **并发与租约**：全实例每分钟最多执行一轮，使用 D1 条件更新租约（90 秒）与公平游标选择到期账号，防止并发写冲突与迟到响应覆写状态。
- **安全约束**：Cookie 仅发往固定 `https://www.v2ex.com` 对应只读路径且不跟随重定向；PAT 请求不带 Cookie；所有上游请求超时 12 秒、响应上限 1 MiB；用户内容不决定请求域名。
- **留存清理**：API 明细保留 7 天（约 5,000 条），API 与 D1 日统计保留 35 天，小时维护按批清理。

### 目录结构

- `worker/`：Worker 入口（`index.ts`）、D1 封装、会话鉴权、首页解析、代理传输与用量统计。
- `worker/notifier/`：账号管理、凭据校验、扫码配对、未读扫描、端到端加密队列、关注提醒采集与记录查询。
- `migrations/`：D1 数据库表结构与增量 SQL 迁移文件。
- `shared/`：前后端共享契约与检查时段工具。
- `src/`：React 19 + shadcn/ui Web 管理台源码（`components/layout/` 布局、`components/ui/` 基础组件、`components/` 业务页面、`lib/api.ts` 状态与请求层、`styles/theme.css` 语义主题令牌）。
- `scripts/`：本地开发初始化（`init-local.mjs`）、独立部署向导与官方 Release 更新脚本（`self-host.mjs`）、预构建发布包打包脚本（`pack-release.mjs`）、部署配置校验（`check-deployment.mjs`）。
- `.github/workflows/`：CI 检查（`ci.yml`）与标签/手动发版打包上传 GitHub Release（`release.yml`）。
- `tests/`：Vitest + Miniflare 测试套件。
- `cloudflare.config.ts` / `deployment-config.ts`：Worker、D1、限流、Secrets、Cron 与可观测性配置。
